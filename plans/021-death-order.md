## 버그

**몹이 용사에게서 먼 쪽부터 사라진다. 가까운 쪽부터 죽어야 한다.**

용사는 무대 왼쪽, 몹은 오른쪽에서 온다(013). 따라서 **가장 가까운 몹은 무리의
가장 왼쪽**이다. 지금은 가장 오른쪽(가장 먼 쪽)부터 사라진다 —
배열 끝에서 빼고 있을 가능성이 높다(`pop()` 또는 인덱스 `n-1`).

사용자가 실기기에서 찾았다. **101개 검사 중 아무도 못 잡았다.**

### ① CORE 인가 VIEW 인가 — VIEW 다. 무엇을 보고 그렇게 판단했나

**CORE 는 개체를 아예 들고 있지 않다.** 확인한 것 넷:

1. **CORE 의 전투 상태는 스칼라 셋뿐이다** — `let foeHP=0,foeMax=0,pHP=0,foeKind`.
   개체 배열이 없다. 배열이 없으니 「배열 끝에서 뺀다」는 CORE 에서 일어날 수가 없다.
2. **`tick()` 의 데미지는 개체를 안 본다** — `foeHP -= dmg` 한 줄이고 `dmg` 는
   `s.dps*0.25` 에 `exec`(`foeHP/foeMax<=0.25`)·`rage`(`pHP/s.hp<=0.50`) 배수뿐이다.
   **둘 다 «비율»이라 어느 개체가 죽었는지와 무관하다.** 받는 피해도 `foeKind`
   (무리 종류)에서만 갈린다. 즉 **소멸 순서가 데미지에 영향을 줄 경로가 없다.**
3. **개체 수는 VIEW 가 파생한다** — `foeCount = 5 + (S.wave*7)%5` (VIEW, 1591행),
   생존 수는 `alive = round(foeHP/foeMax × foeCount)` 로 `drawFoes()`(VIEW)와
   `drawArena()`(VIEW)가 **각자 계산**한다. CORE 는 이 값을 읽지도 쓰지도 않는다.
4. **버그는 그 파생식 옆의 한 줄이었다** — 살아 있는 쪽을 `i < alive` 로 잡아
   **인덱스 끝(= 무대 오른쪽 = 가장 먼 쪽)부터** 지웠다.

그리고 **화면 안에서 이미 자기모순이었다**: 018 의 피격 번쩍임은
`flashing && i===0` 으로 **인덱스 0 을 「맞는 개체」**로 친다. 맞는 놈은 0번(왼쪽),
죽는 놈은 n−1번(오른쪽) — **맞는 놈과 죽는 놈이 서로 반대편**이었다.

→ **CORE 구획은 한 글자도 안 건드렸다.** days.js `81a6288…` 바이트 동일(완주 후).

### ② 고친 자리 — 규약 한 줄 + 그것을 읽는 세 곳

```js
// 죽은 개체는 **앞쪽 (n − alive) 마리**다. 살아남은 개체는 자기 자리에 그대로
// 서 있고(재배치 없음 — 간격·이음매가 안 흔들린다), 무리의 **왼쪽 끝이 물러난다.**
const deadCut=(n,alive)=>Math.max(0,n-alive);
```

- `drawFoes()` DOM 개체 블록: `i>=alive` → **`i<cut`**
- `drawArena()` 무대: `i>=alive` → **`i<cut`**
- 019 묶기: 새로 죽는 슬롯을 `deadCut(n,lastAlive) … cut-1` **오름차순**으로 담는다
  → **호출은 여전히 한 번**이고, 배열 안이 **가까운 쪽부터**다.

`alive` 계산식은 그대로다 — 021 은 **몇 마리가 죽는지**가 아니라 **어느 놈이
죽는지**만 바로잡는다. 018 의 `DIE_MS`·`ATK_*`·소멸 연출은 손대지 않았다.

**검증 창구 신설** — 이 값이 없어서 101개 검사 중 아무도 못 잡았다:
`__view.stage.deadCut`(어디까지 비었나) · `__view.stage.nearest`(지금 가장 가까운
살아 있는 슬롯) · `__view.motion.dieOrder`(사라진 슬롯을 **순서대로**, 상한 32칸 —
검증 창구지 로그가 아니다. 숨김 전환에서 함께 비운다).

### ⑤ 2차 (2026-09-20) — **021 이 낸 회귀의 복구** (판정 ①)

`src/forge.html` 217,866 → **218,434 B** (gzip 72,712 → **72,961 B**).
고친 것은 **한 줄**이다.

```js
-      const cv=foeSprite(kind,tier,ms,stSeg, flashing && i===0);
+      const cv=foeSprite(kind,tier,ms,stSeg, flashing && i===cut);
```

**이것은 018 연출의 변경이 아니라 021 이 낸 회귀의 복구다.** 018 의 의도는 처음부터
「맞는 개체는 용사에게 가장 가까운 것」이었고, 1차가 `deadCut` 으로 앞쪽을 비우기
시작하면서 **인덱스 0 이 빈칸**이 되어 그 의도가 깨졌다. `cut`(= `stage.nearest`)은
그 의도를 글자 그대로 되살린 값이다. **타이밍·지속시간·진폭은 한 글자도 안 건드렸다**
— `FLASH_MS` 34 · `HITSTOP_MS` 50 · `ATK_WIND/HIT/BACK` 150/70/180 그대로이고,
번쩍임 카운터도 그대로 오른다(실측 매회 +1). 바뀐 것은 **어느 자리에서 나는가** 뿐이다.

**실측 — 슬롯별 휘도차(번쩍이는 프레임 − 직전 정지 프레임).** 셰이크가 무대를
통째로 옮기면 상자가 어긋나므로 `reducedMotion` 으로 흔들림만 끄고 쟀다
(018 에서 reduced 는 번쩍임을 **없애지 않고** `FLASH_MS` 만 짧게 한다).

| 죽은 수 | `cut`=`nearest` | 고친 빌드 휘도차 | 옮기지 않은 빌드(`i===0`) |
|---|---|---|---|
| 0 | 0 | `[+31.5,0,0,0,0,0,0,0,0]` → 자리 **0** | `[+31.5,0,…]` → 자리 0 (같다) |
| 3 | 3 | `[0,0,0,+31.5,0,…]` → 자리 **3** | `[0,0,0,0,0,0,0,0,0]` → **아무 데도 안 난다** |
| 6 | 6 | `[0,…,+31.5,0,0]` → 자리 **6** | `[0,0,0,0,0,0,0,0,0]` → **아무 데도 안 난다** |

⚠ **회귀의 실제 모습은 「허공이 번쩍인다」보다 한 단계 더 나쁘다.** 그리는 고리가
`i<cut` 을 건너뛰므로 **백열 판이 아예 안 그려진다** — 번쩍임 카운터는 오르는데
(연출은 돌았다) 화면에는 **아무 일도 일어나지 않는다.** 「돌았다」와 「보인다」가
갈리는 자리다(009 규약). 카운터만 봤으면 이 회귀는 영영 안 잡혔다.

⚠ **cut=0 에서는 두 빌드가 같다.** 만석에서는 인덱스 0 이 곧 가장 가까운 개체라
1차 검증이 못 잡은 것도 이 때문이다 — **검사는 반드시 `cut>0` 인 상태에서 재야 한다.**

참고 그림: `docs/ref/021-flash-sheet.png` — **번쩍이는 그 프레임의 무대**를 두 빌드
× cut 0·3·6 으로 떠 놓았다(스크린샷은 34~84ms 창을 못 잡으므로 `flashing` 이 참인
rAF 콜백 안에서 캔버스를 직접 떠냈다). 고친 빌드는 **살아 있는 가장 왼쪽**이 백열로
뜨고, 옮기지 않은 빌드는 `cut>0` 에서 **아무 개체도 안 뜬다.**
