### 0. 【먼저 읽을 것】 009 의 캔버스가 실은 안 그려지고 있었다

§1 의 「중앙 포커스 — 모루와 화로」를 확인하려고 DOM 을 감추고 캔버스만 찍어 봤더니
**008 이 옮긴 것이 거의 아무것도 화면에 없었다.** 지시서에 없는 결함이지만 §1 이
바로 그 자리를 다시 짜는 일이라 고치지 않고는 §1 을 완료할 수 없어 함께 고쳤다.
(008 §6 때와 같은 판단이다. 대신 아래에 원인·증거·영향을 전부 남긴다.)

**결함 ① 배경의 4분의 3이 화면 밖에 있었다.**
`RenderTexture` 의 기본 원점은 **가운데**다. `rtBg` 를 위치 (0,0) 에 두면 텍스처가
(-w/2, -h/2) 에서 시작해, 구운 배경의 오른쪽 아래 4분의 1만 화면 왼쪽 위에 걸린다.
나머지 화면은 body 단색(`--iron`)이었다 — ART-DIRECTION 이 요구한 무쇠→숯 두 겹이
화면 대부분에서 사라진 상태였다. `rtPanel` 에는 `setOrigin(0,0)` 이 붙어 있고
`rtBg` 에만 빠져 있었다.

**결함 ② 패널 바탕·화로 창·불빛·모루가 통째로 안 그려졌다.**
`RenderTexture.setSize()` 는 **표시 크기만** 바꾸고 밑에 깔린 텍스처는 그대로 둔다.
009 는 `rtPanel` 을 4×4 로 만들어 놓고 매번 `setSize` 로 늘렸으므로, `draw()` 가
4×4 안으로 들어갔다. 화면에는 4픽셀짜리 점 하나만 남았다.

`resize()` 로 바꿔 봤더니 텍스처·카메라 치수는 멀쩡히 바뀌는데 **그 뒤 draw() 가
망가진다** — Graphics 가 첫 채우기의 단색 하나로만 나오고 그라디언트·화로 창·모루가
사라진다. 네 갈래로 나눠 실측했다:

| 만드는 법 | 결과 |
|---|---|
| 처음부터 200×200 으로 만들고 draw | **정상** (그라디언트·타원 전부) |
| 4×4 로 만들고 `resize(200,200)` 후 `fill()` | 정상 (단색이라 표가 안 난다) |
| 4×4 로 만들고 `resize(200,200)` 후 `draw(graphics)` | **깨짐** — 첫 채우기 단색만 |
| 처음부터 460×381 로 만들고 실제 gBrush 를 draw | **정상** |

그래서 **크기를 고치지 않고 그 크기로 새로 만든다** (`makeBg()` / `panelRT()`).
크기가 바뀌면 destroy 후 새로 만들고, 스크롤은 여전히 `setPosition` 뿐이라
009 가 세운 "재굽기 0" 성질은 그대로다. 크기를 30번 흔들어도 텍스처 4개·씬 객체
2개로 고정이고 콘솔 0건이다(누수 없음).

**왜 009 검증이 못 잡았나**: CLAUDE.md 대로 캔버스는 Playwright 가 못 읽어 `__view`
로만 봤는데, `__view.perf` 도 `bgBakes`·`panelBakes` 도 **굽는 횟수만** 셀 뿐
구운 것이 화면에 실제로 올라갔는지는 말하지 않는다. 굽기는 정상적으로 돌고 있었다.
→ 제안 1번(캔버스 픽셀 표본 검사)로 넘긴다.

### 1. 세로 3단 레이아웃

`body` 를 화면 높이의 세로 flex 로 바꾸고 기존 마크업을 세 겹으로 **감싸기만** 했다.
안쪽 id·class·라벨은 하나도 바뀌지 않았다 (checklist 76항목 그대로 통과).

| 단 | 내용 | 성질 |
|---|---|---|
| `#hud` | 웨이브·체력·재화 (기존 첫 패널 + 명판) | `flex:none` — 어느 단이 스크롤되든 항상 보인다 |
| `#focus` | `#forge` (압력계·화로·모루·제련 버튼) | `flex:1` — 남는 세로를 전부 가져간다 |
| `#manage` | 장비·제련 등급·층·테크 | `max-height:30vh` + **자체 스크롤** |

데스크톱은 **좌우로 펼치지 않는다.** `max-width:480px` 을 그대로 두고 가운데 정렬만
한다 — 판이 넓어지면 `aspect-ratio` 타일이 세로로 커져 008 이 고친 하단 차단이
재발한다. 네 크기 전부에서 3단이 유지되고 중앙이 가장 크다:

| 뷰포트 | HUD | 중앙(넘침) | 관리 | 가로 스크롤 |
|---|---|---|---|---|
| 380×820 | 173 | **375** (0) | 246 | 없음 |
| 1280×720 | 175 | **329** (52) | 216 | 없음 |
| 1280×600 | 175 | **245** (136) | 180 | 없음 |
| 1920×1080 | 175 | **581** (0) | 324 | 없음 |

중앙이 모자라면 `#focus` 도 자체 스크롤을 갖는다 (ART-DIRECTION 품질 하한
「세로 공간이 부족하면 반드시 스크롤이 가능할 것」). 화로는 남는 세로를 먹되
**240px 에서 멈춘다** — 안 멈추면 넓은 화면에서 릴 세 칸이 떠 있는 빈 상자가 된다.

**새로 생긴 문제 하나와 그 처리**: 캔버스는 DOM 처럼 `overflow` 로 잘리지 않는다.
`#focus` 가 스크롤되면 패널 바탕이 위아래 단 위로 삐져나온다. `rtPanel` 에
`setCrop` 을 걸어 중앙 창 밖을 잘랐다 — **다시 굽지 않고 크롭만 바꾼다.**
실측: 중앙을 끝까지 내려도 `panelBakes 2 · moves 1`, HUD 구간에 패널 바탕 0.

### 2. 숫자 비트맵 글리프 — 009 파이프라인 재사용

굽는 경로를 `bakePX(픽셀문자열, 폭, 높이, 팔레트, 배율)` **하나로 합쳤다.**
장비 스프라이트와 숫자 글리프가 같은 함수를 쓴다 (`spriteURL` / `glyphURL`).

- **17자 정확히**: `0123456789+-×/%.,` · 셀 5×7 (글자 4×6 + 오른쪽 1열 자간 +
  아래 1행 행간·쉼표 꼬리) · 데이터 **595 B**.
- 자간을 이미지 안에 넣은 이유: img 를 붙여 놓기만 해도 간격이 맞고, **배율을
  올려도 자간이 정수로 따라온다**. CSS margin 으로 벌리면 소수가 된다.
- 쓰는 곳: 웨이브(배율 3 = 숫자(대)) · 최고 · 골드 · 토큰 · 전투력(배율 2).
  한글 라벨은 시스템 스택 그대로다.
- `fmt()` 의 단위 글자(K·M·B·T·e)는 17자에 없다. **알파벳을 그리지 않고** 그 글자만
  시스템 등폭으로 같은 줄에 섞는다 (`.gt`, `::after` 로 그려 textContent 를 안 더럽힌다).
- 값이 **바뀔 때만** 다시 만든다 (`el.__gk` 비교) — 틱당 innerHTML 재구성 없음.
- 숨은 `.gv` 로 같은 문자열을 남긴다 — `textContent` 로 값을 읽는 검사와 보조기술이
  살아 있어야 한다.

`#wv` 만 예외다. **CORE 의 `tick()` 이 `textContent` 로 쓰는 자리**라 손대면 CORE 가
바뀐다. 그래서 `#wv` 는 그대로 두고 (화면에서만 숨김) 옆칸 `#wvg` 에 글리프를 둔다.

**정수 배율 (정지 상태에서, 크기마다 새로 로드)**

| 뷰포트 | 글리프 자연크기 | 표시=자연(1:1) | 스프라이트 배율 | 1:1 |
|---|---|---|---|---|
| 380×820 | 10×14 (2배) · 15×21 (3배) | ✓ | 2배 | ✓ |
| 1280×720 · 1280×600 · 1920×1080 | 10×14 · 15×21 | ✓ | 릴 3배 · 착용 2배 | ✓ |

8배 확대 캡처에서 "1907" 이 전부 균일한 3×3 블록이고 가장자리 번짐이 없다.

| weapon | 0,15,4,12 | 0,15,4,12 | ✓ | 0 |
| head | 1,10,2,13 | 1,10,2,13 | ✓ | 0 |
| body | 1,12,1,15 | 1,12,1,15 | ✓ | 0 |
| legs | 2,12,2,13 | 2,12,2,13 | ✓ | 0 |
| hands | 2,10,2,13 | 2,10,2,13 | ✓ | 0 |

### 4. `gradeRGB()` 캐시 시점

- 8배 확대 스크린샷으로 확인: 15×21 이미지를 3×3 블록 35개로 나눴을 때
  **비균일 블록 0 / 35**, 나머지 0. 유니크 색 2 (투명 + 단색) —
  배율이 PNG 안에 구워져 있고 CSS 가 늘리지 않음이 픽셀로 증명된다.
- 스프라이트도 같이 봤다: `32→32`(모바일) / `48→48`·`32→32`(데스크톱) 전부 1:1.

**t3 판정** — 무기·모자·상의 11등급(t3)과 6등급(t2)을 8배 확대해 나란히 봤다.
t3 는 칼날 안쪽 상감·투구 테두리 하이라이트·흉갑 띠 같은 **내부 세공**만
늘었고 **뿔·날개·가시로 읽히는 외곽 돌출이 없다**. t2 대비 t3 의 경계상자가
여섯 부위 모두 동일하고 t2 밖으로 나간 픽셀 0개 — t3 ⊆ t2.
다만 **t1 은 t2 보다 작아 「세 단계 실루엣 크기 동일」이 t1 에서 깨진다**.
지시서가 범위를 t3 로 못박았고 제안 3 에 이미 올라와 있어 미충족으로만 적는다.
