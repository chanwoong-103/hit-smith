## 배경
004 검증에서 확인된 마지막 미결. `테크 효과 미적용` assert가 고테크 세이브에서
운다. 경계는 spd ≥ 94 / cap = 100 / cost = 100.

원인은 003 §1이 고친 것과 **같은 유형**이다. 현재 세이브의 tech로 잰 값과
만렙 tech를 비교해 "더 좋아져야 한다"를 검사하는데, spd 94면 이미 하한
1500ms에 걸려 있어 더 줄어들 여지가 없다. 001 이전부터 있던 줄이며 003·004가
만든 것이 아니고, 데이터 손상도 없다(004 복원이 뒤에 있다).

## 변경할 것
- 테크 효과 검사를 **하한/상한 포화 구간에서 성립하게** 고친다. 003의
  `onDefaults()` 와 같은 방식으로 **기본 상태(테크 0) 대 만렙**을 비교하거나,
  현재 tech 기준을 유지하되 비교를 `>` 에서 `>=` 로 바꾸는 쪽 중 짧은 것을
  택한다. 포화가 곧 정상이라는 게 이 검사의 전제여야 한다.
- 대상은 최소 3곳: 충전 속도(하한 1500ms), 저장 한도(cap), 강화 비용(-50% 바닥).
  같은 패턴의 다른 검사가 있으면 함께 처리한다.
- `devtools/checklist.js` 에 **고테크 세이브 검사**를 한 줄 추가한다
  (예: spd 99·cap 100·cost 100 세이브 로드 후 assert 0건). 이 유형이 다시
  새지 않게 하는 게 목적이다.

## 바꾸지 말 것
- 테크 공식·하한·상한 **수치 자체** (1500ms 바닥, -50% 바닥 등). 고치는 것은
  검사이지 밸런스가 아니다.
- 003·004가 만든 `newState()`·`onDefaults()`·스냅샷 복원 구조.
- 단일 파일, 무의존.

## 구현 결과 (코딩 세션 2026-08-29)

### 수정 (forge.html — 한 줄 + 주석)

기준선을 현재 세이브가 아니라 테크 0 으로 옮겼다. 두 선택지 중 **"기본 상태
대 만렙"** 쪽이다 — `>=` 로 무르게 바꾸면 테크가 아무 효과가 없어도 통과해서
검사가 사실상 사라지기 때문이다. 이 쪽은 한 줄만 늘고 검사는 그대로 엄격하다.

```js
  S.tech=D.tech;                                   // ← 추가 (D = newState())
  const c0=CHG_MS(), m0=CHG_MAX(), u0=upCost();
  S.tech={spd:100,cap:100,cost:100};
  console.assert(CHG_MS()<c0&&CHG_MAX()>m0&&upCost()<u0,'테크 효과 미적용');
```

`D` 는 003이 만든 `newState()` 반환값이라 새로 만든 구조가 없다. `D.tech` 는
읽기만 하고(참조를 S에 잠깐 얹을 뿐) 004의 스냅샷 복원이 뒤에서 원래 tech 를
되돌린다. 지시서가 말한 3곳(충전 속도·저장 한도·강화 비용)이 모두 이 한 줄
안에 있어서 추가 수정 지점은 없었다.

**같은 패턴의 다른 검사 — 없음.** 자체 점검 안에서 "재고 → 바꾸고 → 비교"
하는 곳은 세 군데 더 있지만(`lvProbs()[9]`, `gradeProbs(0)[GMAX-1]`,
강화 비용 클램프) 전부 기준선을 `S.lv=40` 처럼 **직접 지정한 뒤** 재므로
세이브에 의존하지 않는다. 아래 32조합 스윕으로도 확인했다.

## 제안 (구현하지 말고 여기에 적을 것)

1. 이 오탐은 "포화가 정상인 값을 부등호로 재는" 유형이다. 앞으로 테크·옵션에
   하한·상한을 추가할 때마다 같은 함정이 생긴다. 자체 점검에 **기준선은 항상
   `newState()` 에서 뜬다**는 규칙을 CLAUDE.md 코딩 세션 절에 한 줄로 박아
   두면 세션마다 다시 발견하지 않아도 된다.
2. C3 는 만렙 한 점만 본다. 경계(spd 93/94)는 자체 점검이 세이브를 만들지 않아
   checklist 에서만 볼 수 있는데, 지금은 그 한 칸이 비어 있다. 테크 상한을
   건드리는 지시서가 나오면 C3 를 경계 2점으로 늘리는 것을 권한다.
3. 스윕(32조합)은 이번에 임시 스크립트로만 돌렸다. 세이브 파라미터를 훑는
   검사는 checklist 에 넣기엔 느리므로(약 40초 추가), devtools 에 별도
   `sweep.js` 로 두고 큰 변경 때만 돌리는 편이 맞아 보인다. 계획 세션 판단 요망.
