## 변경할 것

### 1. vendor 반입
- Phaser 3 최신 안정판 min 빌드를 `src/vendor/phaser.min.js` 로 받는다.
- **인라인·CDN 금지** (CLAUDE.md 원칙 2). forge.html 은 `<script src>` 로 참조.
- 파일 크기를 지시서에 기록한다 (원본 / gzip 추정).

### 2. 코어/뷰 구획 분리
- forge.html 스크립트를 주석 배너로 `=== CORE ===` / `=== VIEW ===` 로 나눈다.
- CORE: `tick()`·`S`·`newState()`·저장/복원·self-check·모든 수식·PITY.
  **이 구획은 이번 작업에서 한 글자도 바뀌지 않는다** (아래 완료 조건 참조).
- VIEW: 렌더·DOM 조작·애니메이션. 이후 개편은 VIEW 만 만진다.
- 구획을 나누느라 CORE 코드를 옮겨야 한다면, **옮기기만 하고 고치지 않는다.**

### 3. Phaser 캔버스 초기화
- `dom: { createContainer: true }` 로 게임 생성, 기존 UI 컨테이너를 DOM
  오버레이로 캔버스 위에 얹는다.
- 이번 단계의 캔버스 내용은 **배경(현재 CSS 배경과 같은 톤) 하나뿐**이다.
  모루·파티클·스프라이트는 008~009 몫.
- Phaser 게임 루프와 기존 250ms 틱을 **이중으로 돌리지 않는다.** 기존 틱이
  진실의 원천이고, Phaser 는 그리기만 한다.

### 4. `window.__view` 검증 창구 (이 지시서의 핵심 산출물)
- 캔버스 층이 지금 무엇을 보여주는지 기술하는 평범한 객체를 노출한다.
  최소 구성: `{ engine:'phaser', ready:true, scene:<현재 씬 이름>,
  canvas:{w,h}, overlay:{visible:true}, counters:{shake:0, burst:0} }`
- 카운터는 008 이후 연출이 붙을 자리다. 지금은 0으로 두되 **구조는 만든다.**
- 원칙: `__view` 에 노출되지 않는 연출은 검증 불가이며 완료로 인정하지 않는다.
  앞으로 캔버스에 무엇을 추가하든 이 객체에 한 줄이 함께 늘어야 한다.

### 2. 코어/뷰 구획 분리 — CORE 는 한 글자도 안 바뀌었다

`<script>` 안을 세 구획으로 재배치했다. **코드는 옮기기만 했다.**

```
=== CORE (로직) ===      데이터·상태·확률·스탯·spin·전투(newWave/tick)·
                         sellPrice/resolve/ascend·save·upCost·climb·TILES
=== VIEW (표시) ===      아이콘·drawReel·적 블록·정리 카드·render/renderFast/
                         gateUI·drawOdds·층 팝업·주사위·테크·배선·부팅·Phaser
=== CORE (자체 점검) === 파일 끝
```

**자체 점검만 VIEW 뒤에 남겼다.** 점검이 `foeCount` 처럼 부팅 이후에야 채워지는
값을 읽어서, CORE 블록 안으로 올리면 `newWave()` 가 아직 안 돈 상태로 실행돼
`적 개체 수 5~9 범위 이탈` 이 뜬다. 배너를 하나 더 달아 "위치만 VIEW 뒤일 뿐
내용은 CORE" 임을 명시했다. IIFE 를 함수로 빼서 끝에서 부르는 방법도 있었지만
그건 CORE 수정이라 하지 않았다 (제안 1번).

**CORE 불변 증명 3종:**

### 3. Phaser 캔버스

`<div id="stage">` 를 `position:fixed;inset:0;pointer-events:none` 로 본문 뒤에
깔고 Phaser 를 그 안에 붙였다. `dom:{createContainer:true}`, `Phaser.AUTO`,
`Scale.RESIZE`. 기존 250ms 틱은 그대로고 Phaser 루프에서는 상태를 건드리지 않는다
(이중 틱 없음).

**캔버스는 투명하다 (`transparent:true`) — 지시서와 다른 선택이라 근거를 남긴다.**
지시서 §3 은 "배경(현재 CSS 배경과 같은 톤) 하나"를 그리라고 했다. 그런데 002 가
`body` 에 화로 잔광 그라디언트
(`radial-gradient(...rgba(255,107,44,.15)...)`)를 깔아 두었고, 그 위에 단색
`#171c22` 를 덮으면 **잔광이 사라진다** — "007 전후 육안 동일" 이 깨지고 그건
지시서가 명시한 반려 사유다. 두 조건이 충돌해서 반려 사유가 아닌 쪽을 택했다.
배경의 주인을 캔버스로 옮기는 것은 008 몫이고, 그때 body CSS 의 그라디언트도
같이 걷어내야 한다. `__view.background` 가 지금 `'css'` 이고 008 에서 `'canvas'`
가 되면 된다 (제안 2번).

### 4. `window.__view`

```js
{ engine:'phaser', ready:true, scene:'forge', canvas:{w,h},
  overlay:{visible:true}, background:'css', counters:{shake:0,burst:0} }
```

`globalThis.__view` 로 노출한다 — harness 에는 `window` 가 없어서
`window.__view=` 로 쓰면 node 검증이 통째로 죽는다. 브라우저에서는
`globalThis === window` 라 `window.__view` 로 읽힌다 (완료 조건 그대로 확인).
`canvas` 는 `scale.on('resize')` 로 계속 따라간다.

### 스크린샷 비교 (007 전후, 380px 전체 페이지)

살아 있는 값(충전 카운터·체력바·전이)을 양쪽 다 같은 값으로 못박고 비교했다.
그냥 찍으면 경과 시간 차이가 픽셀 차이로 잡힌다.

| | 값 |
|---|---|
| 같은 페이지 2회 촬영 (노이즈 바닥) | 최대차 1 · 0.15% |

빛난다). 합성 레이어가 하나 생기면서 텍스트가 서브픽셀 → 그레이스케일

> `body` 에 `z-index:1` 을 주는 첫 구현에서는 차이가 14.6% 까지 벌어졌다.
> body 에 쌓임 맥락이 생기면 `background-attachment:fixed` 인 잔광의 래스터화가
> 달라진다. 캔버스를 `z-index:-1` 로 내려 body 를 건드리지 않는 쪽으로 바꿨고
> 2.6% 로 떨어졌다. **픽셀 비교를 안 했으면 못 봤을 회귀다.**

## 제안 (구현하지 말고 여기에 적을 것)

1. **자체 점검을 CORE 블록 안으로 되돌리려면** IIFE 를 `function selfCheck(){}`
   로 바꾸고 파일 끝에서 `selfCheck()` 를 부르면 된다. 두 줄이지만 CORE 수정이라
   007 범위 밖이라 안 했다. 008~011 중 CORE 를 손대는 지시서가 나올 때 끼워
   넣으면 배너가 둘로 갈리지 않는다.
2. **008 은 배경의 주인을 캔버스로 옮기는 일부터 해야 한다.** `body` CSS 의
   `background-image` 그라디언트와 `background-attachment:fixed` 를 걷어내고
   같은 잔광을 캔버스에 그린 뒤 `__view.background='canvas'` 로 바꾸는 것이
   한 묶음이다. 둘 중 하나만 하면 잔광이 두 겹이 되거나 사라진다.
3. **`__view` 검사를 checklist 에 아직 안 넣었다.** 007 의 완료 조건은
   "필드가 존재할 것" 이라 임시 스크립트로 확인했는데, 상시 검사가 없으면
   008 에서 조용히 깨진다. `V-canvas` 류 항목으로
   `ready===true` · 필수 키 존재 · `canvas.w>0` 정도를 넣는 것을 권한다
   (검증 세션 소관). 넣을 때는 CLAUDE.md 규칙대로 **007 이전 forge.html 에
   물려 FAIL 이 나는지** 먼저 확인할 것 — 007 이전에는 `__view` 자체가 없다.
4. Phaser 3.90.0 은 gzip 316KB 다. 게임 코드(26KB)의 12배이고, 첫 로드 체감은
   전적으로 이 파일이 정한다. 008 이후 실제로 쓰는 기능이 파티클·트윈·스프라이트
   정도로 굳으면 커스텀 빌드를 검토할 만하다 — 다만 그건 빌드 스텝이라 원칙 2와
   정면 충돌한다. **지금은 건드리지 말고, 배포 후 실측 로딩 시간을 보고 판단할 것.**
5. `npm pack phaser` 가 4.x 를 준다. 다음에 버전을 올릴 때 무심코 4 를 받으면
   API 가 갈려 007 뼈대가 통째로 깨진다. 버전 교체 지시서에는 반드시
   `phaser@3.x` 를 명시할 것.

### 4. `__view` 상시 검사 추가 (제안 3번 처리 · 검증 세션 소관)

`VC1~VC5` 를 checklist 끝, `C1~C3` 뒤에 넣었다. 위치에도 뜻이 있다 — 바로 앞
세 항목이 페이지를 세 번 리로드하므로, 여기까지 살아 있으면 "리로드 후에도
캔버스가 다시 뜬다"까지 함께 본 셈이 된다.

| 항목 | 무엇을 보는가 |
|---|---|
| `VC1` | 필수 키 7종(`engine/ready/scene/canvas/overlay/background/counters`) 존재 + 타입 |
| `VC2` | `ready===true`, `scene`·`engine` 이 비어 있지 않은 문자열 |
| `VC3` | `canvas.w/h > 0` **그리고 실제 캔버스 엘리먼트 크기와 일치** |
| `VC4` | `background` 가 비어 있지 않은 문자열 (값은 안 박음) |
| `VC5` | `counters` 가 숫자 카운터 묶음, `shake`·`burst` 는 유지 |

**설계 원칙: 값이 아니라 계약을 본다.** 008 이 `counters.bounce` 를 더하고
`background` 를 `'canvas'` 로 바꾸는 것은 정상적인 진행이므로 통과해야 하고,
있어야 할 것이 사라지거나 타입이 무너지는 것만 잡는다. 값을 박아 두면 다음
지시서가 검사를 고치느라 시간을 쓰고, 그러다 검사를 무르게 만든다.

**변이 테스트 (CLAUDE.md 규칙)** — 007 의 checklist 를 그대로 물렸다.

| 변이 | 결과 |
|---|---|
| **A. 007 이전(002 시점) — `__view` 자체가 없음** | VC1~VC5 **5개 전부 FAIL** · 63 통과 5 실패 · exit 1 |
| **B1. `VIEW.ready=true` 제거** | `VC2` 만 FAIL (`ready=false`) |
| **B2. `counters` 에서 `burst` 제거** | `VC5` 만 FAIL (`없는 카운터: burst`) |
| **B3′. `__view.canvas` 를 1×1 로 거짓 보고** | `VC3` 만 FAIL (`{w:1,h:1} vs 실제 {w:380,h:820}`) |
| **B4. `background` 키 제거** | `VC1`+`VC4` FAIL |
| **C. 008 시뮬** (`counters.bounce` 추가 · `particleCap` 키 추가 · `background:'canvas'` · 카운터 값 증가) | **5개 전부 PASS** · 68/68 |

C 가 A~B 만큼 중요하다. 008 이 실제로 할 변경을 미리 흉내내서, **검사가
정상적인 진행을 막지 않는지**까지 확인한 것이다.

> **변이 테스트가 실제로 약한 검사를 잡아냈다.** 처음 `VC3` 은 `w>0 && h>0` 만
> 봤고, 첫 변이(`create()` 의 `VIEW.canvas={...}` 갱신 줄 제거)에서 **통과해
> 버렸다** — `scale.on('resize')` 핸들러가 값을 대신 채우기 때문이다. 변이가
> 의도한 결함을 못 만든 것이고, 동시에 `w>0` 검사는 하드코딩된 숫자도 통과시킨다는
> 뜻이었다. 그래서 `VC3` 을 **실제 캔버스 엘리먼트의 `getBoundingClientRect()`
> 와 대조**하도록 고친 뒤 B3′ 로 다시 물렸다. 통과만 봤으면 아무것도 검사하지
> 않는 검사를 상시 검사로 남길 뻔했다.
>
> 부수 소득: `__view.canvas` 는 `create()` 없이 resize 핸들러만으로도 최신값을
> 유지한다 — 창 크기가 바뀌어도 따라간다는 뜻이다.
